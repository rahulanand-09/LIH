# What L2 needs to run the Axis precheck on L1

For the L2 owner. L1 is ready: every Axis precheck step is a published recipe. L2 calls them through Temporal and
routes only on the outcome labels. A working reference is
`src/test/java/com/rupeek/l1/reference/ReferenceAxisPrecheckWorkflowImpl.java`, about 100 lines, run end to end
by `ReferenceAxisPrecheckFlowTest`. It shows the whole contract in code.

## 1. The two activities

Both are served by the L1 worker on task queue **`lih-l1`**. L2 creates activity stubs with that task queue; the
L1 worker does not need to be in L2's process.

| Activity | Signature | When |
|---|---|---|
| `ResolveRecipes` (`RegistryActivity`) | `Map<String,Integer> resolveRecipes(List<String> refs)` | Once, at case start: pins one version per recipe for the whole case |
| `RunTask` (`TaskActivity`) | `TaskResult runTask(TaskRequest)` | Every lender step |

```java
TaskRequest(String recipeRef, int recipeVersion, String caseId, int runNo, Map<String,Object> inputs)
TaskResult (String outcome, Map<String,Object> outputs, String recipeRef, int recipeVersion, List<StepTrace> steps)
```

- `caseId`: the workflow id.
- `runNo`: the attempt number. Pass the same value in `inputs.runNo`.
- `inputs`: ids only. L1 never puts customer data in inputs or outputs.

**Failures** are `ApplicationFailure` with these types:

| Type | Retry? | Meaning |
|---|---|---|
| `L1_TECHNICAL` | yes | Network, 429/5xx where safe, Mongo transient |
| `L1_UNKNOWN` | **no** | The lender may have received a non-idempotent call (for example Axis 500 or a timeout after sending). Park the case for a human |
| `L1_BUSINESS` | no | Lender said no and the recipe did not map it to an outcome |
| `L1_PERMANENT` | no | Config or data error (for example Core has no loan, or an unknown flag) |

Activity options, as in the reference:
- `startToCloseTimeout` of 5 minutes (the Axis timeouts are 120 s);
- retries with `doNotRetry = L1_BUSINESS, L1_UNKNOWN, L1_PERMANENT`.

## 2. The Axis precheck flow

```
ResolveRecipes(all six) ── once per case
axis.precheck.dedupe     {loanRequestId, runNo, loanProcess}
    IN_PROGRESS ─────────────► end (another attempt owns this loan request)
    INITIATED | ALREADY_INITIATED | REJECTED ─► continue  (lendercore calls Timble even after a failed dedupe; P17)
axis.precheck.timble     {loanRequestId, runNo, loanProcess}
    INITIATED | ALREADY_INITIATED ─► wait for the Timble callback
    REJECTED ─► L2 decision (lendercore would poll forever; suggest: end as FAILED_TO_START or retry later)
on Timble callback:
axis.precheck.timbleCallback {event: <callback payload>}
    TIMBLE_OK | TIMBLE_FAILED ─► poll status        NO_PRECHECK ─► ignore
poll:
axis.precheck.status     {loanRequestId}
    PENDING ─► sleep, poll again (until a deadline)
    SUCCESS ─► precheck.notify.verified {loanRequestId}
    FAILURE ─► precheck.notify.failed   {loanRequestId, lender: "axis"}
    ALREADY_FINAL | NO_PRECHECK ─► end
notify:  NOTIFIED | NOT_ACCEPTED ─► end (a notification problem must not fail the case)
```

All outcome labels and outputs are listed in [`l1-axis-precheck.md`](l1-axis-precheck.md).

## 4. Decisions for L2

1. **Workflow id and attempts.** Today the id is `{lender}-precheck-{customerId}-{loanRequestId}` with
   `REJECT_DUPLICATE`. A re-precheck of the same loan request should be a new attempt with `runNo + 1` (L1 sends a
   new `client_loan_id`). For example, use id `axis-precheck-{loanRequestId}` with `ALLOW_DUPLICATE` once the
   previous run has closed, and carry `runNo` in the start request.
2. **Callback routing.** The callback has `customer_id` but no loan request. There are two options:
   - **(A, recommended)** The callback endpoint runs `axis.precheck.timbleCallback` directly (it does not need
     the case). Its output `loanRequestId` names the case, which L2 then signals so the case moves on to status
     polling. This replaces the visibility query on `customerId`.
   - **(B)** Keep finding the case by `customerId` and run the recipe inside the case, as the reference workflow
     does.

   Both write the same data.
3. **Status polling.** Today rupeekweb's `GET /precheck` triggers the poll. L2 can keep that (an Update that runs
   `axis.precheck.status` synchronously) and/or poll on a timer. The reference polls every 5 minutes, at most 50
   times. Choose the deadline with product.
4. **On `L1_UNKNOWN`:** park the case for an operator instead of failing or retrying.
5. **Timble `REJECTED`** and **dedupe `REJECTED`:** see the flow above (P17 is still open with product).

## 5. Running the L1 worker

- **Turn it on:** in the same app, or a separate one with this repo's L1 code, set `l1.enabled=true` and
  `l1.registry.mode=mongo`.
- **Point it at Temporal:** `l1.temporal.target`, `l1.temporal.namespace`, `l1.temporal.task-queue` (`lih-l1`).
- **Mongo:** the application's `MongoClient` gives the lendercore database; `l1.registry.uri` and
  `l1.registry.database` (`lih_config`) give the registry.
- **Environment variables:** `CORE_TOKEN`, `AXIS_PRECHECK_BASEURL`, `AXIS_PRECHECK_API_KEY`,
  `RUPEEKWEB_ADMIN_TOKEN`. In `local` only, also `CORE_BASEURL` and `RUPEEKWEB_BASEURL`.
- **Config:** publish it with `L1ConfigCli publish` (CI does this; see
  [`l1-config-publishing.md`](l1-config-publishing.md)).
